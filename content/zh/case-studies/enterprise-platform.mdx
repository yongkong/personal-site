## 背景

美国某社会服务机构运行着一个案件管理平台，它的职责直接而有人情味：登记无家可归者，协调他们获得的帮助。每个个案工作者的日常都经过这个系统——它是机构的运营骨架，不是后台辅助工具。

我在 20 人的开发团队里工作了十二年。不能公开的（规模、客户细节）就不公开——值得讲的是架构和这些年的工作本身。

## 我的角色

我负责的是所有其他模块脚下踩着的那一层：

- 网关层——反向代理（YARP）、验证，以及每个服务都要用的公共操作类库
- 统一的数据操作引擎：读取、刷新、更新数据源收敛到一个接口后面，业务团队因此从不手写裸数据访问代码
- 一组独立服务及其多年的升级：Account Server、Chat Server、Library Server
- 横向工具：数据转换工具、短链接服务、数据库复制工具

在二十人的团队里，"负责地基的开发"是一种特殊的信任：你的模块挂了，所有人的都挂。

## 技术决策

平台跨过六代重大演进而没有推倒重写：VB.NET + WinForms → Silverlight → ASP.NET MVC → AngularJS SPA → Angular + .NET Core → .NET 8 微服务。数据层始终是 SQL Server（按负载特性分别用 EF 和 Dapper 访问）；部署从本地服务器走向云。每一代都是在线迁移而非绿地重启——这些升级里沉淀的教训是：长期系统的死因，远多于**被跳过的**升级，而不是被认真做完的大升级。

我最自豪的工作是 SQL Server 到 Oracle 的复制管线。数千万行数据，经 SQL Server Change Tracking 跟踪，由对端的 Windows Service 写入 Oracle。早期版本又慢又偶尔丢数据；最终架构让丢数据在构造上不可能：

- SQL Server 端暴露带前置 CT 健康检查与变更状态查询的 API
- Oracle 端的 Windows Service 批量消费变更：批量插入、结构化错误跟踪、任何漂移立即邮件报警
- 每个阶段都可观测——"同步健康吗"是一条状态查询，不是一次排查

## 结果

十二年，六代平台，零次推倒重写。复制管线从"慢且丢数据"变为千万行规模下快速且精确——同样重要的是，从"只有写它的人能调试"变为"值班的任何人都能操作"。
