我为美国一家社会服务机构的案件管理平台工作了 12 年——登记无家可归者、协调他们获得的帮助。在 20 人的团队里，我负责地基：网关、验证、公共库、统一数据操作引擎，以及 Account、Chat、Library 几个服务和它们的多年升级。

12 年足够把很多"最佳实践"验证成"真的吗"。以下三件事是我最确定的。

## 一、演进不能缺席，但可以按自己的节奏

系统跨了六代：VB.NET + WinForms → Silverlight → ASP.NET MVC → AngularJS → Angular + .NET Core → .NET 8 微服务。每次都是在线迁移，不是推倒重来。

我见过太多系统死法，最常见的不是"大升级升挂了"，而是**一直没升级**——技术债不是线性累积的，是过了某个点突然计息。反过来，认真规划的大升级几乎都能安全落地：我们每代迁移都活着过来了。

> 长期系统死于被跳过的升级，远多于死于被认真做完的大升级。

## 二、守住数据层

我做的一个关键决策是把数据访问收敛成一个统一引擎：读取、刷新、更新数据源，全部走一个接口。业务团队因此从不手写裸数据访问。12 年里前端换了五次脸，数据引擎纹丝不动——**变化频繁的层和变化缓慢的层要分开锁住**。

最艰苦的战役是 SQL Server → Oracle 的复制管线：数千万行、Change Tracking 跟踪、对端 Windows Service 消费。早期版本又慢又丢数据，最终架构让丢数据在构造上不可能：

```text
SQL Server 端                Oracle 端
├─ 前置 CT 健康检查          ├─ Windows Service
├─ 变更状态查询 API          ├─ 批量插入
└─ 批量读取                  ├─ 结构化错误跟踪
                             └─ 漂移即邮件报警
```

## 三、让系统自己会喊疼

同步管线稳定运行的最后一块拼板不是算法，是**可观测性**：错误跟踪、邮件报警、状态查询。"同步健康吗？"从一次排查变成一条查询——这不是锦上添花，这是值班的人能不能睡觉的区别。

12 年维护教会我的元教训：运维的本质不是不出问题，是**问题出现时你已经知道**。

## 这 12 年对客户意味着什么

如果你在评估要不要把系统交给一个人长期维护，看的不是他会不会写代码，而是：他守不守地基、跟不跟演进、建没建可观测性。会写代码的人很多，愿意在场 12 年的人很少。
